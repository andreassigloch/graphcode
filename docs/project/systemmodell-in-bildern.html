Das Systemmodell in Bildern

Wir beschreiben ein technisches System nicht als Fließtext, sondern als Netz aus Bausteinen und Verbindungen. Ein Prüfprogramm legt bei jeder Änderung feste Regeln an dieses Netz an und nennt die Stelle, an der etwas fehlt oder sich widerspricht. Das gilt für Software genauso wie für Mechanik oder Elektrik.

Diese Seite zeigt das Ziel, den Anforderungsbaum eines Beispiels, die zwölf Bausteinarten, die sechs Verbindungsarten, je Regelstufe ein Beispiel, die Methode, die Begriffe dahinter und die Live-Demos. Alle Beispiele stammen aus einem einzigen Fall:

Die Paketstation. Ein Empfänger tippt einen Abholcode ein. Die Station prüft den Code und öffnet das Fach. Zugesagt ist: Das Fach öffnet höchstens 2 Sekunden nach einem gültigen Code.
Für wen:
Jeder Abschnitt zeigt zuerst das Wesentliche. Die Listen dahinter lassen sich aufklappen.

Das Ziel: Abstraktion statt Abbild

Kurz gesagt

Ein Modell bildet ein System nicht 1:1 ab. Es zeigt auf jeder Ebene wenige Blöcke mit einem schmalen Rand; was darunter liegt, bleibt in der Blackbox. Dafür beantwortet es vier Fragen zum System, und jede Antwort lässt sich prüfen.

Kurz gesagt

Der Anforderungsbaum der Paketstation

Kurz gesagt

Links steht der Baum, wie ihn eine gute Spezifikation gliedert: Systemanforderung, Anwendungsfall, Anforderung. Rechts nennt das Modell zu jeder Zeile, wer sie erfüllt und welcher Test sie belegt. Das Modell beantwortet so die Frage „Wer erfüllt das?“. Der Einstieg bleibt der Baum.

Jede Anforderung steht im Satzmuster aus dem Abschnitt „Begriffe“: Wenn Auslöser, dann Ergebnis, innerhalb Güte, nur wenn Bedingung. Ein Verhalten erfüllt eine Funktion. Eine Zusage von Ende zu Ende erfüllt die Wirkkette.

Die sechs Verbindungen

Kurz gesagt

Eine Verbindung hat eine Richtung und eine Art. Welche Bausteinarten sie verbinden darf, ist festgelegt; eine Verbindung außerhalb dieser Liste nimmt das Modell nicht an. Die sechs Arten: besteht aus, gibt ab · nimmt auf, erfüllt, prüft, ist umgesetzt in, gehört zu. Was sich aus anderen Verbindungen berechnen lässt, wird nicht gespeichert.

besteht ausCOMPOSE

Vom Ganzen zum Teil. Die Bausteine bilden damit Bäume: oben das System, unten die Teile. Jedes Teil hat genau ein Ganzes über sich.

Erlaubt: System → System, Anwendungsfall, Anforderung, Modul · Anwendungsfall → Wirkkette, Anforderung · Wirkkette → Funktion · Funktion → Funktion · Modul → Modul · Anforderung → Anforderung · Meilenstein → Anwendungsfall, Anforderung, Funktion

gibt ab · nimmt aufIO

Der Weg, den eine Übergabe nimmt. Er führt immer über einen Datenfluss, nie direkt von Funktion zu Funktion. Darum hat jede Übergabe ein Format.

Erlaubt: Akteur → Datenfluss → Funktion · Funktion → Datenfluss → Funktion · Funktion → Datenfluss → Akteur

erfülltSATISFY

Wer eine Anforderung einlöst. Ein Verhalten erfüllt eine Funktion. Eine Güte wie Zeit, Gewicht oder Durchsatz erfüllt die Wirkkette (Ende zu Ende), ein Modul (lokales Budget) oder das System.

Erlaubt: Funktion → Anforderung (Verhalten) · Wirkkette, Modul, System → Anforderung (Güte)

prüftVERIFY

Welcher Test welche Zusage belegt. Ein Datenformat bekommt einen eigenen Vertragstest, der auch die Fälle prüft, die es ablehnen muss.

Erlaubt: Test → Anforderung · Test → Datenformat

ist umgesetzt inALLOCATE

Wo eine Funktion wohnt. Jede unterste Funktion liegt in genau einem Modul. Die Kopplung zwischen Modulen wird daraus berechnet, nicht behauptet: Modul A hängt an Modul B, wenn eine Funktion aus A einen Datenfluss an eine Funktion aus B gibt.

Erlaubt: Funktion → genau ein Modul

gehört zuRELATION

Zuordnungen ohne Hierarchie: ein Fluss zu seinem Format, ein Auftrag zu seinem Meilenstein und zu den Bausteinen, die er ändert, ein Meilenstein zu seinem Nachfolger.

Erlaubt: Datenfluss → genau ein Datenformat · Auftrag → Meilenstein · Auftrag → Anwendungsfall, Anforderung, Funktion, Modul, Datenformat · Meilenstein → Meilenstein (kommt nach)

Was sich berechnen lässt, wird nicht gespeichert. Ob zwei Module voneinander abhängen, folgt aus den Funktionen, die in ihnen liegen, und den Datenflüssen zwischen diesen Funktionen. Welcher Akteur welchen Anwendungsfall auslöst, folgt aus dem Datenfluss in die erste Funktion seiner Wirkkette. Solche Verbindungen gibt es im Modell nicht als eigene Elemente. Eine behauptete Verbindung könnte von der tatsächlichen abweichen, eine berechnete nicht.

Dieselbe Landkarte, gefüllt mit dem Beispiel. Jede Frage an das System hat hier eine Antwort: wozu (Anwendungsfall und Anforderung), wie (Wirkkette und Funktionen), worüber (Datenflüsse und ihr Format), womit (Module) und womit belegt (Test).

Regeln und Stufen

Kurz gesagt

80 Regeln prüfen das Modell bei jeder Änderung. Jede Regel gehört zu einer von zwölf Stufen, die der Entstehung eines Modells folgen, vom System bis zum Abgleich mit der Umsetzung. Hinter fünf Stufen liegt eine Marke, ein Abnahmepunkt. Jeder Befund nennt den Baustein und den nächsten Schritt; nur wenige Regeln blockieren, die meisten geben Hinweise.

Die Stufe nennt die Bausteinart, die es geben muss, damit die Regel greift. Eine Regel über Tests schweigt, solange es keine Tests gibt. Drei Regeln gelten in jedem Zustand. So bleibt die Menge je Arbeitsschritt beherrschbar: Auf einer Stufe greifen 1 bis 12 Regeln, dazu die drei, die immer gelten. Wer das System anlegt, hat 4 Regeln vor sich. Alle 80 gelten erst beim Abgleich mit dem Bau.

Hinter manchen Stufen liegt eine Marke, ein Abnahmepunkt. Eine Marke ist erreicht, wenn bis zu ihr kein Befund mehr offen ist. Die Marken sind die üblichen Prüfpunkte der Systementwicklung.

Jeder Befund hat eine Schwere. Blockiert heißt: Die Änderung, die den Befund neu einführt, wird nicht angenommen. Hinweis heißt: Sie wird angenommen, der Befund bleibt sichtbar, bis er behoben ist. Jede Regel nennt den betroffenen Baustein und den einen nächsten Schritt.

Die Methode: geführt, nicht gegängelt

Kurz gesagt

Das Modell entsteht Zug um Zug. Der Nutzer sagt, was er will, ein KI-Agent baut einen kleinen Schritt, das Modell urteilt und antwortet mit dem nächsten Vorschlag. Der Nutzer entscheidet, der Agent führt aus. Vier Stufen: Das Tor unterbindet, das Gummiband steuert, die Vorschläge empfehlen, und in der vierten Stufe gestaltet der Autor die Architektur über Constraints: Entscheidungen wie „20.000 gleichzeitige Abholungen pro Sekunde“, die als Anforderung mit Test im Modell stehen und den Schnitt der Ketten und Module bestimmen. Kennzahlen finden Stellen, Constraints steuern.

1
Unterbinden

Das Tor

Jede Änderung geht durch dasselbe Tor, ob Mensch oder KI sie vorschlägt. Es blockiert nur, was die Änderung neu an Fehlern einführt. Altlasten bleiben sichtbar, halten aber niemanden auf.

2
Steuern

Das Gummiband

Die Reihenfolge der Stufen ist ein Vorschlag, keine Pflicht. Der Nutzer darf vorgreifen, etwa Module entwerfen, bevor alle Anforderungen stehen. Übersprungene Stufen erzeugen Hinweise, keine Blockade. Sie ziehen wie ein Gummiband zurück zur vollständigen Spezifikation: nach jedem Zug ein Satz an den Nutzer mit dem nächsten Schritt.

3
Empfehlen

Die Vorschläge

Auf Anfrage nennt das Modell Umbauzüge, die seine schwächste Stelle entschärfen: eine Funktion in ein anderes Modul legen, eine Zwischenebene einziehen. Jeder Vorschlag wird durch das Tor geprobt, ohne zu speichern. Angewendet wird nichts automatisch.

4
Gestalten

Constraints

Die Architektur bestimmt der Autor, im Modell: als nicht-funktionale Anforderung an eine Wirkkette, ein Modul oder das System, mit einem Test, der das Modell selbst prüft. Ein Umbauzug, der sie bricht, macht den Test rot.

„Das Netz aus Stationen verarbeitet 20.000 gleichzeitige Abholungen pro Sekunde.“ Eine zentrale Codeprüfung trägt das nicht: Die Prüfung wandert in die Station, die Zentrale verteilt die Codes vorab. Der Test prüft, dass kein Schritt der Kette „Abholung“ auf die Zentrale wartet.

Details: der Zug, die Gestaltungsregeln, der Vergleich von Alternativen, die Constraint-Dimensionen

Wie der Steuerwert Entscheidungsalternativen vergleicht

Der Steuerwert nimmt von jeder gemessenen Stelle den Abstand zur Schwelle und merkt sich den schlechtesten. Ein Modell ist so gut wie seine schlechteste Stelle: Ein gutes Modul kauft kein schlechtes frei, und keine einzelne Regel diktiert allein. Null heißt, jede Stelle liegt innerhalb ihrer Schwelle.

Hat der Agent mehrere Alternativen für einen Zug, reicht er alle als Probe durch das Tor und vergleicht die Urteile in dieser Reihenfolge:

  1. Eine Alternative, die das Tor blockiert, scheidet aus.
  2. Weniger offene Befunde auf der Stufe, an der gerade gearbeitet wird.
  3. Kein Anstieg blockierender Befunde an anderer Stelle.
  4. Ein Zug, der nichts löscht, geht vor einem, der löscht. Weniger Modell ist kein besseres Modell.
  5. Entschärft der Zug die schlechteste Stelle, also sinkt der Steuerwert?
  6. Erst danach zählt, wie viel der Zug anlegt.

Für Umbauvorschläge am fertigen Entwurf gilt eine Grenze, die gemessen wurde: Kennzahlen zeigen, wo ein Vorschlag eingreift und was dazu zu lesen ist, sie ordnen die Vorschläge nicht. Die Wahl zwischen zwei vertretbaren Entwürfen trifft der Autor, und er hält sie als Constraint fest.

Vor dem ersten Schnitt fragt der Agent je Dimension nach einem Element und einer Eigenschaft, nie nach einer Zahl für die Dimension selbst. Ein Constraint zählt nur, wenn ein Zug am Modell ihn brechen kann, ohne dass sich das Verhalten der Umsetzung ändert.

Begriffe: Was und Wie, Blackbox und Whitebox

Kurz gesagt

Jeder Baustein hat eine Definition in einem Satz, mit Beispiel und Gegenbeispiel aus der Paketstation. Eine Anforderung sagt, was ein Element an seiner Grenze tut oder einhält, nie wie. Blackbox ist ein Element von außen gesehen, Whitebox dasselbe Element von innen. Drei Bausteine lassen sich so schachteln: System, Funktion, Modul. Die Schnittstelle einer Blackbox wird aus den Flüssen über ihre Grenze berechnet, nicht behauptet.

Die zwölf Bausteine in je einem Satz

Der Satz ist die verbindliche Definition. Die Quelle nennt die Standarddefinition, der er entspricht.

Eine Abweichung von den Quellen ist gewollt: Die Funktion trägt bei uns zusätzlich die Regel „die unterste Ebene ist an eine Umsetzung gebunden“. Das ist eine Prüfregel, kein Teil der Definition.

Format, Träger und Verfeinerung einer Übergabe

Wer eine Übergabe vereinbart, muss drei Fragen beantworten. Welcher Art ist sie? Worüber läuft sie? Wie genau soll sie beschrieben sein? Im Modell haben die drei Antworten feste Plätze, und keine braucht ein neues Element.

Die Art folgt aus dem Format. „Volumenstrom 0 bis 20 l/min bei 6 bar“ ist hydraulisch, „Pegel 0 bis 5 V“ elektrisch, „Drehmoment 2 Nm“ mechanisch, „Fachnummer 1 bis 48“ logisch. Die Einheit sagt es; ein Merkmal „physisch“ oder „logisch“ am Fluss gibt es nicht. Die Familie hat das gemessen: Die früheren Merkmale für Protokoll und Güte am Fluss waren in 0 von 186 Übergaben gesetzt und sind entfallen.

Der Träger ist ein Modul. Kabel, Bus, Leitung, Welle, Tastatur sind Teile, die man baut oder kauft. Sie erscheinen als Modul, in dem die sendende oder empfangende Funktion liegt. Hat der Träger eigenes Verhalten, das zählt, etwa Laufzeit auf dem Bus, bekommt er eine eigene Funktion in der Kette. Sonst bleibt er weg: Zwei Funktionen im selben Programm übergeben direkt.

Verfeinert wird über Funktionen, nicht über Formate. Ein Fluss hat genau ein Format und keine Teile. Wer die Übergabe genauer beschreiben will, setzt Funktionen ein: einpacken, übertragen, auspacken. Zwischen ihnen entstehen neue Flüsse, jeder mit eigenem Format. Das ist eine längere Kette, keine Schichtung. Drei Formate für dieselbe Übergabe gibt es nicht; es gibt drei Übergaben zwischen verschiedenen Funktionen.

Zwei Fehler, die das Modell meldet. Ein Format, das Inhalt und Träger mischt („6 Ziffern über Bluetooth“): Der Träger gehört in ein Modul, nicht ins Format. Ein Fluss mit zwei Formaten, etwa Fachnummer und CAN-Frame zugleich: Dazwischen fehlt die Funktion, die einpackt.

Plug-and-Play folgt daraus von selbst: Das Format am Inhalt bleibt, die Funktionen fürs Übertragen lassen sich tauschen, und mit ihnen der Träger.

Eine Anforderung sagt das Was, nie das Wie

Die Regel: Eine Anforderung nennt nur, was an der Grenze ihres Trägers sichtbar ist. Sichtbar an der Grenze sind drei Dinge: der Akteur oder Nachbarschritt, die Übergabe mit ihrem Format, und eine messbare Eigenschaft. Sobald der Satz ein inneres Teil, einen inneren Schritt oder eine Technik nennt, ist er ein Wie und gehört in die Whitebox.

Die Tiefe ist erlaubt, der Blick nach innen nicht. Eine Anforderung am Schritt „Code prüfen“ bleibt ein Was, solange sie nur dessen Grenze beschreibt. Ob ein Satz ein Was ist, hängt vom Träger ab: Für die Station ist „Fach öffnet in 2 s“ ein Was. Für den Schritt „Code prüfen“ wäre derselbe Satz keiner, weil das Fach nicht an seiner Grenze liegt.

Was

„Code prüfen“ liefert zu jedem 6-stelligen Code innerhalb von 200 ms die Antwort gültig oder ungültig.

Wie

„Code prüfen“ vergleicht den Code gegen die SQLite-Tabelle der Steuerung und sendet das Ergebnis über CAN.

Empfohlenes Satzmuster für funktionale Anforderungen. Auslöser und Ergebnis sind Übergaben, die Güte ist eine Zahl mit Einheit, die Bedingung ein Zustand. Die ersten beiden sind Pflicht, die anderen nach Bedarf. Ob das Muster eine Prüfregel wird, entscheidet ein Versuch am Bestand.

Beispiel. Wenn ein gültiger Code eingegeben wird, dann öffnet das Fach, innerhalb von 2 s, nur wenn die Tür geschlossen ist.

Blackbox und Whitebox

Blackbox ist ein Element von außen gesehen: seine Grenze, was hinein- und hinausgeht (Datenflüsse mit Format), was es zusagt (Anforderungen) und womit das belegt ist (Tests). Kein Blick nach innen.

Whitebox ist dasselbe Element von innen gesehen: seine Teile und die Übergaben zwischen ihnen. Jedes Teil ist wieder eine Blackbox. Was Blackbox und was Whitebox ist, hängt davon ab, welches Element man gerade betrachtet.

Schachteln lassen sich genau drei Bausteine: System, Funktion, Modul. Auf der Landkarte tragen sie das Zeichen ↻. Eine Wirkkette ist keine Box: Sie ist die Whitebox des Systems für einen Anwendungsfall, und jedes ihrer Glieder ist eine Blackbox. Ihr Rollup fasst Glieder für die Anzeige zusammen, er schachtelt nicht.

Die Schnittstelle einer Blackbox wird berechnet, nicht behauptet. Sie besteht aus allen Datenflüssen, deren Erzeuger innen und Abnehmer außen liegt, oder umgekehrt. Von außen und von innen ist es dieselbe Schnittstelle.

Die Treppe: Anforderung und Lösung auf jeder Stufe

Die Trennung von Anforderung und Lösung liegt nicht an einer festen Stelle im Modell. Sie wiederholt sich auf jeder Stufe: Links steht, was ein Element an seinem Rand zusagt. Rechts steht, wie es das eine Stufe tiefer erreicht. Was rechts als Teil auftaucht, hat auf der nächsten Stufe wieder einen eigenen Rand mit eigener Zusage.

Eine Funktion nur zur Gliederung gibt es nicht. Jede Funktion erfüllt eine Anforderung, sonst meldet Stufe 5 sie als Ballast. Eine Funktion mit Teilschritten und eine Blattfunktion unterscheiden sich nur darin, was hinter ihrem Rand liegt: Teilschritte oder ein Verweis auf die Umsetzung. Beide tragen Anforderungen, beide haben eine berechnete Schnittstelle. Der Modulbaum ist keine Stufe der Treppe. Er steht daneben und nimmt die Blattfunktionen auf.

Module schachteln sich genauso. Ein Modul von außen ist ein Rand mit den Übergaben, die ihn kreuzen, und mit seinen Gütezusagen, etwa Gewicht oder Antwortzeit. Von innen sind es Teilmodule und die Funktionen, die darin liegen. Die Treppe der Module läuft neben der Treppe der Funktionen, bis unten ein Teil liegt, das gebaut oder gekauft wird: eine Datei, eine Platine, ein Gehäuse. Die Übergaben zwischen zwei Modulen werden nicht eingetragen, sondern aus den Funktionen berechnet, die in ihnen liegen.

Heute zeichnet der Viewer einen Fluss von außen bis zu dem Teil, das ihn aufnimmt. Anschlüsse am Rand, ein Steckbrief je Blackbox und der Kapselungsbefund am Rand sind als Auftrag CR-GVE-400 im Viewer-Repo beschrieben.

Bestand einlesen und Anforderungen zusammenführen

Kurz gesagt

Wer ein bestehendes System spezifiziert, fängt nicht leer an. Lastenhefte, Datenblätter und Code liegen schon vor, und dieselbe Anforderung steht darin mehrfach, mal in anderen Worten, mal mit anderer Zahl. Der Anwendungsfall „Bestand erschließen und Anforderungen zusammenführen“ beschreibt den Weg zum einen Baum: jede Anforderung einmal, mit Quelle, Widersprüche als Fragen.

Ausgangslage: zwei Dokumente zur Paketstation

Lastenheft Paketstation
  1. Das Fach öffnet sofort nach Eingabe des Codes.
  2. Nach drei Fehlversuchen wird die Eingabe gesperrt.
  3. Die Station meldet jede Abholung an den Versand-Server.
Pflichtenheft Schließmechanik
  1. Öffnung innerhalb von 3 s nach Codeeingabe.
  2. Sperre 60 s nach 3 falschen Codes.
  3. Der Riegel zieht ab 11 V Versorgungsspannung.

Orange: dieselbe Anforderung zweimal. Rot: ein Widerspruch, „sofort“ gegen „3 s“.

Der Ablauf in fünf Schritten

  1. Gliederung zeigen

    Das Werkzeug liest beide Dokumente und zeigt ihre Gliederung als Baum: Kapitel, Unterkapitel, Größe je Abschnitt. Kein Sprachmodell, gleiche Datei ergibt immer denselben Baum.

    Skill se:import-doc, Stufe 1 · PDF braucht pdftotext

  2. Typen entscheiden

    Im Chat entscheidet der Auftraggeber, was jedes Kapitel wird: „Anforderungen“ wird zu Anforderungen, „Abnahme“ zum Test, der sie prüft, der Anhang fällt heraus. Eine Anforderung ohne prüfenden Test nimmt das Gate nicht an; darum fragt der Agent hier nach dem Test.

    Skill se:import-doc, Stufe 1 · Ergebnis: eine Liste von Entscheidungen

  3. Auszug durch das Gate

    Ein Sprachmodell zieht aus jedem Abschnitt Anforderungen, Funktionen und Module. Jeder Fund geht durch dasselbe Gate wie jede Handänderung. Das Einlesen fügt nur hinzu; es löscht nichts, was schon im Modell steht.

    Skill se:import-doc, Stufe 2 · braucht einen erreichbaren Endpunkt für das Sprachmodell

  4. Code einlesen

    Liegt Code vor, liest das Werkzeug daraus Funktionen, Module und Datenflüsse, ohne Sprachmodell. Anwendungsfälle und Anforderungen liest es nicht aus dem Code; die kommen aus den Dokumenten. Der Vorzustand des Modells wird vorher gesichert, und das Ergebnis trägt den Stempel der Modellversion.

    Befehl graphcode import-code · Wirkketten „Modell einlesen“ und „Code einlesen über den Skill“ im Modell

  5. Zusammenführen

    Der Agent legt die doppelten Anforderungen nebeneinander und stellt jeden Widerspruch als Frage: „sofort oder 3 s?“ Der Auftraggeber antwortet „2 s, nur bei geschlossener Tür“. Aus den sechs Sätzen der beiden Dokumente werden die Anforderungen A1, A4, A6 und A7 des Baums, jede einmal.

    Handarbeit im Chat, jede Änderung durch das Gate

Ergebnis: der Anforderungsbaum der Paketstation weiter oben. Die übrigen Anforderungen kommen aus weiteren Quellen oder aus dem Gespräch mit dem Auftraggeber.
